# MapLibre + Three.js GLB custom-layer rendering

This document records the verified rendering path for local GLB facade/window geometry in `test.html`. Keep these rules when adding or repairing other Three.js models so the earlier invisible-layer bug is not reintroduced.

## 1. MapLibre GL JS 5.x render callback

The custom layer must use `type: 'custom'` and `renderingMode: '3d'`.

In MapLibre GL JS 5.x, the render callback receives a render-input object, **not the projection matrix array directly**. Use:

```js
render(gl, args) {
  const mainMatrix = args?.defaultProjectionData?.mainMatrix;
  if (!mainMatrix) return; // Also report this condition in the UI while debugging.
  const values = Object.values(mainMatrix);
  if (values.length !== 16 || values.some(v => !Number.isFinite(Number(v)))) return;
  const mapProjection = new THREE.Matrix4().fromArray(values.map(Number));
  // Compose mapProjection with the model transform, then render.
}
```

Do not revert to `render(gl, matrix)` followed by `new THREE.Matrix4().fromArray(matrix)`. That treats the callback argument as an array and can leave the GLB loaded but entirely invisible.

## 2. Reuse MapLibre's WebGL context safely

Create the renderer with the map's existing canvas and GL context:

```js
renderer = new THREE.WebGLRenderer({
  canvas: map.getCanvas(),
  context: gl,
  antialias: true
});
renderer.autoClear = false;
```

Before and after the Three.js render, call `renderer.resetState()` so Three.js and MapLibre do not leave each other's WebGL state corrupted. After loading the model or changing visibility, call `map.triggerRepaint()`. Keep the custom layer above solid building layers when facade geometry must remain visible.

## 3. Coordinate-system rule for this GLB

The facade model is generated by `ermita/scripts/generate_facade_details.py` from building polygons transformed to **EPSG:3857**. Its local X/Y values are differences in **projected Web Mercator metres**, recentered around the saved origin. Its local Z values represent building-height metres around the vertical origin.

Read the exact anchor from:

- `complete_data/OSM/data/buildings/windows/facade-model-origin.json`

The model transform therefore uses different scale factors:

```js
const anchor = maplibregl.MercatorCoordinate.fromLngLat(
  { lng: origin.longitude, lat: origin.latitude },
  origin.anchor_altitude_m
);
const groundMeterScale = anchor.meterInMercatorCoordinateUnits();
const projectedXYScale =
  groundMeterScale * Math.cos(origin.latitude * Math.PI / 180);

const modelTransform = new THREE.Matrix4()
  .makeTranslation(anchor.x, anchor.y, anchor.z)
  .scale(new THREE.Vector3(
    projectedXYScale,
    -projectedXYScale,
    groundMeterScale
  ));
camera.projectionMatrix.copy(mapProjection).multiply(modelTransform);
camera.projectionMatrixInverse.copy(camera.projectionMatrix).invert();
```

Why: `meterInMercatorCoordinateUnits()` converts a **ground-distance metre** at the anchor latitude to Mercator world units. EPSG:3857 X/Y are already stretched by the Mercator projection's latitude factor, so multiply the X/Y scale by `cos(latitude)` to avoid scaling the horizontal geometry twice. Z is a physical height, so it retains the unadjusted ground-metre scale. The negative Y scale converts north-up projected coordinates to the map's screen/world Y direction.

If a future GLB is authored in local **ground metres** rather than EPSG:3857 projected metres, do not apply this cosine correction blindly; record the GLB's actual coordinate system and use the matching transform.

## 4. Keep the model origin tied to the generated GLB

The origin JSON is written by the same generation run as the GLB and uses the exact set of prepared building polygons. Do not estimate a new anchor from the map center or from a different footprint dataset. Avoid rounded or separately copied origin values where the origin JSON can be loaded directly.

For alignment QA, verify these items before regenerating the GLB:

1. Confirm the origin JSON belongs to the exact GLB being loaded.
2. The facade generator reads `ermita/maps/generated/ermita-building-details.geojson`. Its exact committed copy is `complete_data/OSM/data/buildings/ermita-building-details.geojson` (1,533 features: 1,528 polygons and 5 points). The active `ermita/maps/generated/ermita-building-footprints.geojson` is documented in `docs/data-source-catalog.md` as basemap geometry, despite its name; its copy under `complete_data/OSM/data/buildings/ermita-building-footprints.geojson` therefore must not be used as the alignment reference for this OSM-derived GLB. The test page now uses `ermita-building-details.geojson` for the underlying OSM building extrusion layer so both are based on the same source geometry.
3. Compare a few recognizable building corners close to the anchor and farther away. A nearly constant displacement suggests a translation/origin mismatch; a displacement that grows with distance suggests a scale/projection mismatch.
4. Check the model bounds and vertex count in the browser. Successful GLB loading proves the geometry was parsed, not that the render callback and coordinate transform are correct.
5. During diagnosis, render a visible anchor marker or bounds helper independent of the GLB material. Remove diagnostic coloring only after alignment is confirmed.

## 5. Current working implementation

The active diagnostic implementation is in `test.html`, layer ID `windows-facade-details`, controlled by checkbox `#osm-windows`. Keep the MapLibre 5.x matrix handling and the EPSG:3857 horizontal scale correction together; they solve different problems (render visibility and geographic alignment).
